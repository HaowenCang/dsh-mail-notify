## 2. What actually changed between `0.1.7-rc.2` and `0.2.0-rc.2`

The migration is narrow, and stating it narrowly is the point: a report that
claims a broad rewrite would be as wrong as one that claims nothing changed.

### 2.1 The admission gate reads `peerDependencies`

`@deepseek-ai/dsh-app-boot`'s own README states the rule that governs whether a
profile may load this plugin:

> Before a profile imports a plugin, DSH checks its `peerDependencies` on
> `@deepseek-ai/dsh` and `@deepseek-ai/dsh-*` against the single runtime version
> returned by `getDshRuntimeVersion()`. Every declared range must match;
> prereleases participate in range matching. […] Missing DSH peers impose no
> constraint; invalid ranges are incompatible. These checks use peer
> declarations, not `engines.dsh` […]
> — `dsh-app-boot/README.md`, installed `0.2.0-rc.2`

Two consequences decide this release:

1. Only `@deepseek-ai/dsh` and `@deepseek-ai/dsh-*` peers are matched.
   `@deepseek-ai/cordis`, `@deepseek-ai/schemastery` and `react` are **not** part
   of the verdict, so their ranges stay as they are.
2. The match is against one exact runtime version. `0.1.7-rc.2` cannot satisfy a
   `0.2.0-rc.2` runtime, and no range can be widened to admit both without
   claiming an untested pairing.

### 2.2 The Host's question and approval vocabulary

`0.2.0-rc.2` ships two modes under the one `ask_user_question` tool name — the
legacy blocking call, and an opt-in timed call whose foreground wait may close
with a `pending` result while the question remains answerable. A human who
answers afterwards produces a user-role message whose `source.kind` is
`user-question-reply`.

This is a Host-side change to *what events exist*, not to the contracts the
plugin's source names. The plugin observes `tool/call` and classifies user
messages by `source.kind`, so it needs no timed-specific branch. §6 and §7 state
what was verified to hold, not merely that no code changed.

### 2.3 The client contracts did not change

`src/client/contracts.ts` records the checked claim: the form types, the slots
package's `SlotMap`, the connection handle, the locale registry and the
settings-controller Remote are identical to `0.1.7-rc.2`, and the Plugins-page
owner props differ only in type-only assembly imports. The two compatibility
compile probes are the check, and they compile against the installed `0.2.0-rc.2`
typings (§9).

### 5.3 The classification rule, restated

Only `source.kind === 'user'` makes a message the operator's prompt. A late
`user-question-reply` is a user-role message, so it must not become the turn's
`includeUserPrompt` content — and §5.2 asserts it does not, under
`includeUserPrompt=true`. Timed-only fields such as `timeout` never enter a mail
body, and the `ask_user_question` argument allowlist stays strict.

## 6. Late `user-question-reply` handling

**Terminology correction, no re-run.** The harness's single expected-label list
was later split into its two real classes — 23 Config labels and one write-only
password Credential label — and its assertion name and comment were rewritten to
state what the check actually proves. The selectors, the label matching, the
other 25 checks, and the assertion count are unchanged, so the recorded
**26 / 26** remains the result of the current script: no executable behavior
changed and the browser run was deliberately not repeated for a comment-level
correction.

Three findings worth recording, because each is the kind that a weaker harness
would have recorded as a pass:

- **A control count is not a field check.** The first version of the harness
  asserted a count. The v0.4.0 report had to retract exactly such a conclusion
  (`V0.4.0_COMPAT_REPORT.md` §18 note and §27), and the harness was then
  strengthened from a tally to an explicit list of expected **display labels**:
  the 23 Config labels, matched one at a time against the rendered `<label>`
  text, plus the one separate write-only password Credential label. A missing
  Config control can no longer hide behind an unrelated extra control, and the
  Config claim is not derived from the total 24 — `22 + 2` and `23 + 1` are the
  same number, and only the second is the configuration surface.
- **That label check is rendering evidence, not a key-set comparison.** The
  expected labels are the card's own handwritten copy, not a set derived from
  the Host's describe mirror, so the browser harness would keep passing if the
  Host schema gained a field nobody listed in it. The Host/Web **key-set
  equality** is a different check in a different evidence class: it is enforced
  by `tests/client/config-surface.test.ts` **PAR-01**, which derives the Host
  Config field set from `Config.toJSON()` and compares it against the card's
  `ALL_FIELDS` in both directions, including duplicate detection. It is part of
  the passing unit suite in §13. Calling the browser label comparison a "key-set
  comparison" would overstate what it proves; the two checks are complementary,
  and §18 records both.
- **A refusal looks like a success at the HTTP layer.** The first commit attempt
  was refused by the Host — `smtpUser is required and must be a non-empty user
  name` — and the page rendered "The host did not accept the save." The RPC
  answered 200. The harness now reads the envelope and fails on `ok:false`,
  naming the Host's own words.

**Not covered by the browser run:** a real completion / question / approval
notification *driven from the Web UI*. The isolated web profile composes the real
model provider, so driving a Turn there would spend a real plan's quota. Those
families are covered by the real-assembly probes of §5, §10 and §7 instead, whose
substitutions are the human, the model's tokens and the SMTP peer's identity.

The claim is evidenced, not asserted:

- The operator's live listener on `19387` was recorded before and after the
  browser run and kept the same owning PID.
- Probe homes are created fresh per run and live under `_isolated`; the
  isolation root and profile name are supplied on the command line
  (`DSH_MAIL_NOTIFY_PROBE_ROOT`, `DSH_MAIL_NOTIFY_PROBE_PROFILE`) rather than
  inherited from source defaults.
- **Credential isolation, both directions.** The synthetic browser password is
  present in `E:\Projects\DSHarness\_isolated\...\.credentials.yaml` (positive
  control) and absent from `C:\Users\20659\.dsh\.credentials.yaml`, which still
  holds only the operator's own three references. No live profile was copied into
  the test environment; each disposable profile was created from a shipped
  template and given only the test's own loopback SMTP settings.
- The operator's `.dsh` directory does change during a session — it is the
  harness's own session store, and it holds this session's and its subagent's
  transcripts. That is the harness writing its own records, not this plugin's
  tests writing a profile: none of the probe sentinels or test credentials appear
  anywhere under it.

### 20.2 The one correction it produced

The probe comment at `host-contracts.compile.ts` claimed `MessageSourceMap['user']`
was "the *only* kind that may populate the ordinary user-prompt field". That is
true of the `kind` **value** and false of the member set: a second member,
`'user-rpc'`, carries `kind: 'user'` and is the browser's prompt. It is declared by
`@deepseek-ai/dsh-api-session-controller` at
`lib/types/types.d.ts:375-383`, which this session verified directly in the
installed tree.

The comment is corrected. It now states that the discriminator is the value, that
two members carry it, and what a member-name match would actually cost: every
prompt typed in the Web UI would stop counting as the operator's own words.
Behaviour was already right — `src/event-handler.ts` compares the value — so this
is a documentation fix, not a behaviour change.

The assertion was deliberately **not** added to the probe. Naming
`MessageSourceMap['user-rpc']` requires importing a package this plugin does not
otherwise depend on, and adding a dev dependency purely to name one member would
make the probe's dependency list claim more than the plugin uses. The fact is
recorded from the installed typings instead, and that choice is written into the
probe beside the claim.

### 20.3 Two evidence-class caveats, recorded rather than papered over

1. **"Removed in DSH 0.1.7".** `tests/compatibility/contracts.compile.ts` and
   `src/client/contracts.ts` attribute the removal of `ctx.settingsScope`,
   `settings.plugin.item` and `SettingsScope` to `0.1.7`. That attribution rests
   on the v0.4.0 session having had `0.1.7-rc.2` **installed** — which is exactly
   where `V0.4.0_COMPAT_REPORT.md` §4 reads its old→new mapping from. That tree is
   no longer on this disk, so neither this session nor the audit could re-derive
   it; the strongest re-derivation available now bounds the change to
   `(0.1.5-rc.2, 0.2.0-rc.2]`. The claim is kept on the prior session's
   installed-tree evidence, and this note exists because its evidence class
   differs from every other claim in this report.
2. **Two probe rows rest on a plugin-declared augmentation.** The assertions on
   `ctx.connection.rpc.call(...)` and `ctx.connection.isLoopback` are grounded in
   a `Context` member that `src/client/contracts.ts` declares itself, because
   `dsh-client-connection` augments `Context` for its host entry only. The
   `ConnectionHandle` type is imported from DSH, so a change to its members is
   still caught; a change to *which entry declares it* would not be. The plugin's
   own comment states this, and §9.3 repeats it.
