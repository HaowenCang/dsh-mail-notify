## 2. What actually changed between `0.2.0-rc.2` and `0.2.1-rc.2`

The migration is narrow, and stating it narrowly is the point. Full per-surface source
evidence is in [`docs/compat/01_CONTRACT_DIFF.md`](docs/compat/01_CONTRACT_DIFF.md); the
plugin-side usage inventory is in [`docs/compat/02_PLUGIN_USAGE_AUDIT.md`](docs/compat/02_PLUGIN_USAGE_AUDIT.md).

### 2.1 The admission gate now reads `engines.dsh` first

At tag `dsh-v0.2.1-rc.2`, `packages/boot/app-boot/src/plugin-compatibility.ts` evaluates
a plugin manifest as follows:

- If the manifest declares its own `engines.dsh` string, that range **alone** decides
  admission; `peerDependencies` are not read on that branch
  (`plugin-compatibility.ts:55-61` at the NEW tag).
- Only when `engines.dsh` is absent does it check every `@deepseek-ai/dsh` and
  `@deepseek-ai/dsh-*` peer against the runtime version with
  `semver.satisfies(runtime, range, { includePrerelease: true })` (`:62-73`).
- A non-object `engines` or non-string `engines.dsh` is a malformed manifest and is
  refused; a `workspace:` value in `engines.dsh` can never be satisfied.
- The refusal record and wording changed from `peerDependencies {…}` to
  `requirements {…}`.

At tag `dsh-v0.2.0-rc.2` the same file read **only** `peerDependencies`; `engines.dsh`
was ignored entirely. The runtime version is the `dsh-app-boot` package version, the same
string `dsh --version` prints.

Consequences for this plugin: the published `0.5.0` declares no `engines.dsh` and pins
its `dsh-credentials` / `dsh-session` peers at `0.2.0-rc.2`, so the fallback rule rejects it
on a `0.2.1-rc.2` host — the refusal is reproduced in §4.1. The `0.5.1` declaration
(§3) passes natively — §4.2.

### 2.2 The host surfaces the plugin calls did not break

Source comparison at the two exact tags found the following **identical or additive-only**
for every surface the plugin touches (details and file:line in
[`docs/compat/01_CONTRACT_DIFF.md`](docs/compat/01_CONTRACT_DIFF.md)):

- `SessionEvent` payloads, the session envelope, and the format version (stays 4):
  `turn/start`, `step/start`, `assistant/message` (including `d.usage`), `user/message`
  (including `source.kind`), `tool/call`, `tool/result`, `turn/end` and its reason map,
  `SessionHeader` (`origin`, `delegationDepth`, `agentPreset`, `parentSession`, `isSeeded`).
  Additive-only: plugin records, a few known event types, and an optional `principal` on
  the `user-rpc` source.
- Approval audit events (`approval/asked`, `approval/decided`) are unchanged; only an
  internal invariant module was deleted.
- Timed `ask_user_question`: `tool-ask-user` and `user-questions` sources are
  byte-identical between the tags. The timeout result is still a non-error
  `{ pending: true, callId }`; a late answer is still a user-role message with
  `source.kind === 'user-question-reply'` keyed by `callId`.
- Token usage (`TokenUsage`) and the telemetry schema-v2 candidate contract are unchanged.
- `loader/volatile-update` has the same name and signature at both tags
  (`vendor/loader/src/index.ts:34`; emitted at `config/entry.ts` OLD:189 / NEW:191), and
  the volatile commit semantics are unchanged (`vendor/cordis`, `vendor/cosmokit`,
  `vendor/schemastery` sources identical; only version bumps).
- `connection.fetch.register` route shape and its single-argument `fetch(request)` are
  unchanged; the client `connection.rpc.call(channel, endpoint, payload, signal)` is
  source-identical. Host-only breaking changes (`HostConnectionHandle.operator` →
  `browserPeer`, ownership-scoped exact routes) do not affect a plugin whose browser half
  is the owner page client.
- `plugins.bundle.config` slot declaration and `PluginConfigViewProps` are unchanged.
- `configForms.get()` / `whileServed()` are unchanged; **one member was removed**:
  `ConfigFormSnapshot.mode`, together with the client memory-persistence mode. The plugin
  never read `.mode`; the compile probe now states the removal as a checked
  `@ts-expect-error` (§5).

### 2.3 Behaviour changes that are compatible but observable

- **Credential read priority inverted.** The file-backed provider now prefers the managed
  store over the inherited process environment (0.2.0 did the opposite), reports
  `describe().writable = true` for environment-sourced refs, no longer refuses an
  environment-shadowed `set`/`unset`, and warns instead of failing on unknown YAML keys.
  The public `resolve`/`describe`/`set`/`unset` API is unchanged. This plugin never
  implements a priority of its own and never caches the secret: it resolves the named
  reference once per send attempt, so it needs no code change — but which layer wins is
  now the Host's decision. Observed live on the target host: `resolve()` returned the
  file-layer value (`source: file`) and `describe()` reported `configured: true,
  writable: true` (§9).
- **HMR was rewritten.** Instead of requiring a restart for a profile package change,
  0.2.1 stops and evicts the affected Loader entries, then recomposes and restarts them;
  a stop runs the fiber's disposers, which is where this plugin releases its listeners,
  queue and timers. The plugin-side lifecycle is unchanged, and the duplicate-listener /
  duplicate-mail question is a runtime question, answered in §10.
- **The shipped `headless` bundle disables the credential store.** At the NEW tag,
  `packages/bundle/headless/cordis.patch.yml` sets `credentials`, `authorization` and
  `deepseek-account` to `disabled: true` for one-shot jobs; `0.2.0-rc.2` had no such rows.
  On a stock one-shot profile a credential-referenced SMTP password therefore cannot
  resolve, and the plugin deliberately refuses with `credential-missing` rather than
  failing open. The `dsh-headless` README documents the restore recipe; Web and desktop
  profiles keep the service. This is a host-profile behaviour change with a documented
  remedy, recorded in `README.md`, `docs/DSH_INTEGRATION.md` and the release notes, and
  it is why the probe overlays restore the row (§6.1).
- **Client surface.** `ConfigFormSnapshot.mode` removed (see above); `ui-slots` remains a
  published package and remains the slot registry (the plugin imports only its types, so
  it is not required in the host's runtime tree); `dsh-client-ui-settings`,
  `dsh-client-ui-plugin-manager`, `dsh-client-connection`, `dsh-api-remotes` and
  `dsh-client-locale` keep every member this plugin names. Both compatibility compile
  probes are the check (§5).

### 3.1 Why `engines.dsh` is the only host-range declaration

`0.5.1` declares no `@deepseek-ai/dsh` peer, deliberately:

1. DSH `0.2.1-rc.2`'s own plugin-authoring guide
   (`docs/user/develop/basic/publish.md` at the tag) designates `engines.dsh` as the
   declaration of the DSH releases a package supports and names DSH peer ranges as the
   fallback consulted only when `engines.dsh` is absent — the exact rule the gate
   implements.
2. The plugin imports no host package; its runtime imports are `nodemailer` and the host
   services it resolves through `ctx`.
3. npm and pnpm install a root host peer. Declaring one pulled the entire DSH application
   into this repository's dependency tree: 700 packages instead of 163, and
   `npm audit --omit=dev` reported 8 moderate advisories from host tooling (the launcher's
   optional office/PDF stack) instead of 0. A consumer install would inherit the same.

The two peers that remain — `dsh-credentials` and `dsh-session` — are exact `0.2.1-rc.2`
because they name the shared service instance the plugin resolves at send time and the
declarations it type-imports. With `engines.dsh` present the gate does not read them; they
are an instance declaration, not a second compatibility range. The direct gate-function
evaluation in §4.3 shows both mechanisms were checked.

### 3.2 Exact pins, one line at a time

The peers stay exact, and the new `engines.dsh` is exact as well. A range that admitted
both `0.2.0-rc.2` and `0.2.1-rc.2` would be accepted by the Host — which is precisely the
danger: it would turn "one verified pairing" into "two pairings, one untested" with the
Host's approval. `0.5.1` therefore claims `0.2.1-rc.2` only; `0.5.0` remains the
`0.2.0-rc.2` line and is not re-declared.

## 10. Lifecycle, HMR and queue

The plugin's start/stop contract did not change, and the 0.2.1 HMR rewrite was exercised
on the real host rather than argued from source:

- **Stop** runs the fiber teardown, which clears the three session listeners, the
  `loader/volatile-update` listener, the dedupe and the queue; the teardown is idempotent.
- **Volatile remount** (enable/disable through the live configuration) keeps exactly one
  listener set: after the switch, the event-driven mail deltas measured on real Web-UI
  Turns were **1 (baseline) → 1 (after volatile remount) → 0 (disabled) → 1 (re-enabled)**,
  with a final status of `active:true, queue depth 0`. No duplicate mail was sent.
- **Package update while the Host is running** (0.2.1's live reload path): a CLI
  `dsh plugin add` of the archive was accepted while the host ran (`Already up to date`,
  pnpm relink); the next Turn produced exactly one mail, and a full Host restart kept
  exactly one mail per event with a drained queue.
- **Listeners and queue after reload** are therefore observed to be neither duplicated nor
  leaked in the paths above. Bound: a *client-bundle* HMR swap is not separately asserted
  — no claim is made about client-module hot replacement beyond what the browser run
  observes after a reload.

## 14. Known limitations

1. **`0.2.1-rc.2` is the only claimed host.** The new `engines.dsh` is an exact pin for
   that reason. No `0.2.1` final, no `0.2.2` prerelease, and no `0.2.0-rc.2` support is
   claimed by `0.5.1`; `0.5.0` remains the `0.2.0-rc.2` line.
2. **The tag↔npm-artifact link is supplied, not derived.** The npm tarball of
   `@deepseek-ai/dsh@0.2.1-rc.2` carries no `gitHead`, so the tag commit is recorded from
   the task; the measured fact is the runtime string `0.2.1-rc.2` and the exact installed
   package versions.
3. **One host-profile behaviour needs a profile-level remedy.** A stock `0.2.1-rc.2`
   *headless* profile disables the credential store; a credential-referenced SMTP password
   there must be restored at the profile level (documented in README/release notes). This
   is a host change with a host-documented remedy, not a plugin defect, and Web/desktop
   profiles are unaffected.
4. **The browser run does not drive a real model completion.** The isolated web profile
   composes the real model provider, so driving a Turn there would spend a real plan's
   quota. The notification families are covered by the real-assembly probes, whose only
   substitutions are the model's tokens, the human, and the SMTP peer's identity.
5. **The HMR duplicate-listener check is observational.** The probe and browser runs
   observe one mail per event after a live reload and no leaked queue, but a source-level
   guarantee of "exactly one listener after any interleaving" is not claimed beyond what
   §10 states.
6. **The compatibility gate is an admission check, not a sandbox.** It reads the
   declaration; it cannot make untrusted plugin code safe.
