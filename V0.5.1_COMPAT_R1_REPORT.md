### 3.2 Headless credential-service documentation (R1.3)

The wrong sentence appeared in `README.md` (install note and troubleshooting table),
`docs/DSH_INTEGRATION.md`, and `RELEASE_NOTES_V0.5.1.md`: restore the credential rows
**"or supply the password through the launch environment."**

`src/credentials.ts` shows why that alternative is false: `getCredentialProvider()`
reads `ctx.get('credentials')`; when the service is absent, `resolveSmtpPassword()`
returns `credential-missing` and never reads the launch environment directly.

All four places now distinguish:

- **DSH's own model API-key resolution** in the headless profile: launch environment,
  then `<cwd>/.env`, then `$DSH_HOME/.env` (per the host's headless README);
- **this plugin's SMTP password**: a `CredentialRef` resolved only through the
  Credential service (`ctx.get('credentials')` → `resolve()`/`describe()`), so with
  `credentials` disabled there is no service to call and an exported variable alone is
  not read.

The documented remedy is the official one from the target tag's
`packages/bundle/headless/README.md` §Credentials: restore the `credentials`,
`authorization` and `deepseek-account` rows in the profile patch (or a `--patch`
overlay). No bypass code was added; the plugin still fails safe with
`credential-missing`.

## 4. R1.4 — Conflict test: precedence, fallback, rotation

### 4.1 Test design

`tests/integration/credential-precedence.test.ts` (part of `npm test`) spawns
`tests/support/credential-precedence-child.mjs` with:

- an isolated `DSH_HOME` (fresh `mkdtemp` directory under
  `tmp/phase051-r1/credential-precedence-tests/`);
- synthetic value **A** in `$DSH_HOME/.credentials.yaml` (managed `refs:` section);
- a *different* synthetic value **B** exported as `DSH_MAIL_SMTP_PASSWORD` in the
  child's inherited process environment;
- the installed `@deepseek-ai/dsh-credentials-local@0.2.1-rc.2` provider mounted on a
  real Cordis context with the real `launchEnvironment` snapshot factory;
- a third synthetic value **C** for the rotation phase.

The child asserts `process.env[DSH_MAIL_SMTP_PASSWORD] === B` before resolving, so the
conflict is proved to exist. It then performs three operations through the provider:

1. `resolve()` and `describe()` with both layers present;
2. `unset()` (real provider write), then `resolve()`/`describe()`;
3. `set(C)` (real provider write), then `resolve()`/`describe()`.

Results are the target provider's own answers; no test assertion was adjusted to force
a pass.

| FALLBACK | `unset(A)` | B (`source: env`) | `configured: true`, `source: env`, `writable: true` | **PASS** |

Provider versions reported by the child: `dsh-credentials-local 0.2.1-rc.2`,
