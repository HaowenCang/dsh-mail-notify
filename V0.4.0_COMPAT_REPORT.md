## 3. Root causes

**CONFIRMED — the DSH 0.1.7 configuration surface was replaced, not extended.**

| Retired in 0.1.7 | Present instead | Where the fact was read |
| --- | --- | --- |
| `ctx.settings.installSection(owner, ns, schema, entry, hooks)` | `ctx.settings` is `SettingsForms`: `describe` / `update` / `replace` / `mutate` / `configure` / `whileServed`; a namespace *is* a profile entry id | `dsh-settings/lib/types/index.d.ts` (installed `0.1.7-rc.2`) |
| `ctx.settingsScope.bind({ namespace })` | `ctx.configForms.get(entryId)` → `ConfigForm<T>`, plus `ctx.configForms.whileServed([...])` | `dsh-client-ui-settings/lib/types/client/config-form.d.ts`, `config-form-types.d.ts` |
| `settings.plugin.item` as the plugin-configuration card surface | `plugins.bundle.config` (keyed by package name) for a bundle's own configuration; `plugins.item` is the Official group of standalone cards | `dsh-client-ui-plugin-manager/lib/types/client/slot-contract.d.ts` and the page's own render calls |
| configuration persisted to `$DSH_HOME/settings.yaml` | the profile's `cordis.patch.yml`, written through `dsh-config-editor` | `dsh-config-editor/lib/index.js`, `dsh-settings/lib/index.js` |

`installSection` is not a renamed method with the same meaning; it is a different architecture. The
plugin's editable configuration is now generated **from its Config schema**, which is why no
compatibility shim can exist: a shim would have to synthesize the form the user edits, and that form
is derived from the schema by DSH.

**Additional root cause found only by running the target (see §7):** the session-format-v4 lifecycle.
DSH 0.1.7 opens `turn/start` before the queued input is entered and writes the input as an unnumbered
`user/message` **followed by** two injected context messages. The pre-fix rule ("keep the latest user
text") therefore attributed the wrong message.

## 6. Peer-range decision

**CONFIRMED by measurement, and it reverses the intuitive answer.**

```text
semver.satisfies('0.1.7-rc.2', '^0.1.5-rc.2')            → false   (default range semantics)
semver.satisfies('0.1.7-rc.2', '^0.1.5-rc.2', {includePrerelease: true}) → true
```

DSH's own compatibility preflight evaluates peer ranges with `includePrerelease: true`
(`dsh-app-boot/lib/index.js`, `evaluatePluginCompatibility`), so the old `^0.1.5-rc.2` range would
have *passed* the preflight against `0.1.7-rc.2`. That is exactly why it must not be kept: a range
that admits an untested prerelease is a compatibility claim the evidence does not support.

The peers are therefore **pinned**:

```json
"@deepseek-ai/dsh-credentials": "0.1.7-rc.2",
"@deepseek-ai/dsh-session": "0.1.7-rc.2"
```

Cordis and Schemastery keep shared-major ranges (`^4.0.4`, `^3.18.4`), because those two must be one
instance shared with the host and pinning them invites a second, mutually invisible service registry.
The plugin does not declare `@deepseek-ai/dsh` itself as a peer.

Not advertised by any range: DSH `0.1.5`, `0.1.6`, a `0.1.7` final, `0.1.8`, or any later RC. None
was exercised, and §3 shows the break is bidirectional, so there is no shared-support region to
describe even in principle.

## 7. Host configuration migration

### 7.1 Schema shape

All 23 fields are top-level volatile scalars. Schemastery rejects a volatile field with a volatile
ancestor or under a container node — measured directly:

```text
OK    scalar boolean / scalar with min-max / array of scalars / union scalar
THROW array of objects, element volatile   $.a.*.b volatile fields require a fixed object path …
THROW root transform over volatile object  $.*.a   volatile fields require a fixed object path …
```

So `smtp` / `policy` / `render` / `retry` exist only in the derived `ResolvedConfig`; the stored
document is flat. `scripts/probe/volatile-shape-probe.mjs` and `scripts/probe/schema-probe.mjs`
record the experiments and run against an explicitly staged `schemastery@3.18.4` +
`cosmokit@1.8.5` pair (`npm run probe:volatile`, `npm run probe:schema`).

### 7.2 One snapshot boundary

```text
Volatile Config  →  snapshotOf(config)  →  ResolvedConfig
```

`snapshotOf` reads each field exactly once. Nothing downstream of it holds a `Volatile` reference, so
the mailer, queue, policy, and event handler cannot observe a half-applied update. `ConfigSnapshot`
is a closed interface rather than a conditional type over the schema: a deeply readonly array does not
reduce to `string[]` through `infer`, and an assertion would have bought silence at the cost of the
check. `scripts/type-probes/host-contracts.compile.ts` asserts that the snapshot is closed.

### 7.3 Live reconfiguration

`entry.update` (the Loader) treats a change that touches only volatile fields specially: it re-resolves
the candidate through the plugin's `Config`, calls `updateVolatile` on each moved reference, and emits
`loader/volatile-update`. `bindVolatileConfig` subscribes to that event and rebuilds the runtime from
a fresh snapshot. Defaults and validation limits are unchanged from `0.3.1`.

### 7.4 Cross-field validation, and where it actually happens

This is the one place where the target's real behaviour differed from the obvious design, and the
correction is worth recording.

The natural implementation is a root-level `Schema.transform` holding the cross-field rules. It
**cannot work**: Schemastery rejects a volatile field under a transform node (`$.*.a volatile fields
require a fixed object path…`), so wrapping the object schema in a transform destroys the form.

What actually enforces the rules is `dsh-config-editor.edit`, which resolves the candidate through
the plugin's own `Config` **before** it persists anything:

```js
const resolved = fiber.ctx.waterfall(fiber, "internal/config", next, () => next)
resolveConfig(fiber.runtime, resolved)   // throws → the write is refused
```

Field-level constraints therefore live on the field schemas (so a refusal names the field), and the
cross-field rules stay in `resolveConfig` as the runtime's defence in depth. A hand-edited patch
never passes through the editor, which is why both layers are needed.

Measured refusal messages (§8.3) confirm the ordering: nothing is written when either layer refuses.

> **Corrected in the RC closure — see §25.** The paragraph above conflates two different functions
> that are both named `resolveConfig`. The one in the snippet is imported from
> `@deepseek-ai/cordis`; the one that held the cross-field rules is this plugin's own
> `src/config.ts::resolveConfig`, which cordis never calls. The Host therefore enforced **only** the
> field-level constraints at the time this section was written, and a field-valid but
> product-invalid configuration could be persisted. §25 records the correction; §7.4a and §7.4b
> record the mechanism now in place and what it refuses.

### 7.4a The pre-persistence mechanism (RC closure)

The plugin's entire Host pre-persistence validation surface is the **standard-schema** contract on
its exported `Config` node. `@deepseek-ai/cordis`'s `resolveConfig(runtime, config)` is:

```js
if (!runtime.Config) return config
const result = runtime.Config['~standard'].validate(config)
if ('then' in result) throw new TypeError('Async config validation is not supported')
if (result.issues) throw new ValidationError(result.issues)
return result.value
```

`.check()` is not used because the pinned release has no such method: `Schema.prototype` in
`@deepseek-ai/schemastery` `3.18.4` — verified against both this checkout's copy and the one the
installed DSH `0.1.7-rc.2` ships — exposes `~standard`, `toJSON`, `set`, `push`, `i18n`, `extra`,
`required`, `disabled`, `collapse`, `hidden`, `loose`, `deprecated`, `experimental`, `pattern`,
`simplify`, `toString`, `role`, `default`, `link`, `comment`, `description`, `max`, `min`, `step`,
and `volatile`, and nothing else. A root `Schema.transform` is not an alternative either, for the
reason this section records.

The exported node is therefore *derived* — `new Schema(fieldSchema.toJSON())`, the same
reconstruction `dsh-settings`'s `plainSchema` performs — with an own `~standard` property shadowing
the inherited getter. The inherited validator runs first, so a field-level violation is still reported
by the field schema with Schemastery's own path, and the product rules are consulted only when that
result is clean. On success the inherited result is returned unchanged, so the Loader still commits
the resolved volatile tree. The rules themselves live in one module, `src/config-check.ts`, and both
boundaries call that one copy.

`scripts/probe/config-check-probe.mjs` establishes the five properties the task named — the absence of
`.check()` and therefore its (non-existent) callback signature, primitive-versus-wrapper input, the
root object remaining a valid form, a failing check refusing before any write, and the check being
absent from the serialized form — against the exact installed Schemastery, and it runs against both
copies. The result table is recorded in `docs/DECISIONS.md` D021 §2.1.

### 7.4b What the Host now refuses, and what it does not

Only while `enabled` is true: `smtpHost` non-empty and whitespace-free; `smtpUser` non-empty; `from` a
plausible non-empty address under the project's existing rule; `to` yielding at least one valid
recipient after normalization and deduplication. `smtpPasswordCredential` stays governed by its
field-level `pattern()`, because the field schema already refuses a malformed reference and a
cross-field duplicate would report the same refusal twice.

`enabled: false` bypasses all of them, so an incomplete document stays legal and saveable — the user
story the task requires, and the state `scripts/probe-host-config-write.mjs` opens with. The three
warning-only rules are explicitly **not** errors: port 587 with `smtpSecure: true`, port 465 with
`smtpSecure: false`, and every notification switch false. The probe asserts both directions,
including that a warning-only write is *accepted*.

### 7.5 `enabled` lifecycle

`enabled = false` still means: no session listeners, no queue worker, no SMTP runtime, and no
credential resolution for sending. The one listener that remains is `loader/volatile-update` — without
it the plugin could not hear the switch being turned back on, which would make `false → true` require
a restart. `CFG-*` and `SUP-05` cover this; the browser run in §8 shows `false → true` activating the
runtime with no restart.

## 8. Client surface migration

### 8.1 What registers where, and why not `plugins.item`

The card registers into `plugins.bundle.config`, keyed by the **package** name `dsh-mail-notify`.

This is a deliberate departure from the structure the task text anticipated (`plugins.item`, keyed by
`dsh-mail-notify`). The installed slot contract states what each slot is for, and the page's own
render calls confirm it:

- `plugins.item` is the page's **Official** group: *"One official plugin the Plugins page lists in its
  Official group after the official bundles… OCCUPIED by the official settings pages, one companion
  package per host-plane namespace."* A bundle's configuration is explicitly directed elsewhere.
- `plugins.bundle.config` is *"A bundle's own configuration, keyed by the bundle's package name and
  rendered on the bundle's page"* — resolved by the page as `renderSlot('plugins.bundle.config', {
  view: 'page' }, { entryKey: pkg.name })`.

`dsh-mail-notify` is an installed bundle, so the second is its surface. The two are not
interchangeable in either direction: a `plugins.item` registration would move the form to a standalone
card in the Official group, away from the row whose enable switch and component list live on the
bundle's page, and it carries a required `id`/`label` pair that a bundle has no identity for. The
registration is additionally gated by `ctx.configForms.whileServed([entryId], …)`, so a deployment
that installs the package but disables the entry shows no configuration section at all.

Both strings are asserted against their sources: the entry id against the shipped `cordis.patch.yml`
(`CFG-10`), the package name against the published `name` field and the `plugins.bundle.config` key
(`tests/package/tarball.test.ts`, `contracts.compile.ts`).

### 8.2 Contract checking

`tests/compatibility/contracts.compile.ts` (client program) and
`scripts/type-probes/host-contracts.compile.ts` (host program) are compile-time assertions that are
never executed. They name the published types rather than restating them, and they assert the retired
names as *checked absences* via `@ts-expect-error`. Verified that those directives bite: removing the
one guarding `ctx.settingsScope` fails the build with
`Property 'settingsScope' does not exist on type 'Context'. Did you mean 'settingsSchema'?`, and

The two probes are two files because `ctx.connection` is `ConnectionHandle` in the browser entry and
`HostConnectionHandle` in the host entry; one program sees both augmentations and can compile neither.

### 8.3 The card

Behaviour preserved from `0.3.1`, verified in the browser on a disposable profile:

- one collapsible disclosure, collapsed by default, `aria-expanded` / `aria-controls` per instance;
- bilingual copy through the DSH locale seat, switching live;
- effective value per field, with an `inherited` badge or a per-field `Reset`;

## 9. RPC decision

**KEEP `connection.fetch.register`.** No migration to `rpc.handle` was attempted, because the
evidence for the existing choice still holds and the alternative remains unusable:

- `HostConnectionRpc.intercept('/api', …)` admits exactly one interceptor and `/api` is already
  claimed by the Typert gateway.
- `HostConnectionRpc.handle('<channel>', …)` exists in the type surface, but the `0.1.5` finding that
  its implementation reads `owner.webServer` from the *providing* context was not re-tested here. It
  is optional cleanup, not a release blocker, and an untested rewrite of a working transport would be
  a worse outcome than a documented non-decision.
- `HostConnectionFetch.register(route)` publishes an exact route that the shared handler consults
  before the interceptor, inheriting `/api`'s trust fence and session authentication.

The `0.1.7-rc.2` host handle still exposes all three
(`scripts/type-probes/host-contracts.compile.ts` asserts `fetch.register`, `rpc.handle`,
`rpc.intercept`, and `createSharedFetchHandler`). `src/web-rpc.ts` is unchanged.

**CONFIRMED end to end** in the fresh-install run: the browser called
`api/dsh-mail-notify/status` and `api/dsh-mail-notify/test-email` through
`ctx.connection.rpc.call`, and the test-email route answered
`{"ok":true,"value":{"delivered":true,"recipientCount":1}}` with the message arriving at the loopback
SMTP server.

## 10. Session-v4 findings

Measured from a live two-Turn run (`tmp/live-policy/out/events.log`, produced by
`scripts/probe/event-order.mjs`):

```text
seq=   4 type=turn/start     turn=1
seq=   6 type=step/start     turn=1 step=1
seq=   8 type=user/message   turn=-  text="PROBE_PROMPT_A_alpha …"
seq=   9 type=user/message   turn=-  text="Current runtime context. …"
seq=  10 type=user/message   turn=-  text="<system-reminder> A skill is a reusable …"
seq=  15 type=assistant/message turn=1 step=1
seq=  17 type=turn/end       turn=1 reason=completed
seq=  19 type=turn/start     turn=2
seq=  23 type=user/message   turn=-  text="PROBE_PROMPT_B_beta …"
seq=  26 type=turn/end       turn=2 reason=completed
```

Confirmed by that ordering:

1. **`turn/start` precedes the input.** A turn is open before the operator's prompt is in the log.
2. **The prompt carries no turn number.** Attribution must come from the open turn, not from the
   payload.
3. **Injected context follows the prompt, in the same role.** Two user-role messages that are not the
   prompt arrive after it, and they are *user* messages rather than system ones.

The pre-fix rule kept the latest text, so Turn 1 rendered the skill reminder and Turn 2 rendered its
own prompt — the prompt was lost and the shift was invisible in the mail count. The fix: a turn takes
the **first** non-whitespace user message as its prompt, in one of two ways — seeded from the pending
buffer at `turn/start`, or attributed directly to the open turn when the message arrives after the
turn opened — and every later user message in that turn is context. `UP-01`…`UP-07` cover the rule
and its lifecycle; `probe:user-prompt` covers it end to end.

> **Superseded in the RC closure — see §25.4.** The rule described above — *first non-whitespace user
> message* — was itself replaced. It is a positional rule, and position is the one thing v4 does not
> promise; the kind declared in `UserMessage.source` is. Attribution is now by `source.kind ===
> 'user'`, with the most recent direct-human message of a turn winning. The lifecycle findings 1–3
> above remain correct and are unchanged.

`SESSION_FORMAT_VERSION = 4` was not read as a constant by this plugin at any point, before or after:
the plugin's structural adapter consumes named events, and the session format number never entered
its logic. That is why the format bump itself required no change, while the lifecycle *inside* v4 did.

## 11. `forked` handling

`dsh-session` declares the seventh `turn/end` reason kind:

> Fork-seed construction closed a turn that was still open at the fork boundary in the source session.
> Only fork seeds carry this marker — the loop never emits it — and the source events before the
> boundary remain intact in the child.

Implemented as: an explicit `CONFIRMED_KINDS` member, an explicit `CandidateStatus` (`forked`), and an
explicit `classifyCompletion` case. It is mapped to no policy switch, so nothing is fabricated for a
turn that never settled — neither success nor failure nor a token-limit stop — and it is deliberately
**not** folded into `unknown`, because one is a recognised marker and the other is an unrecognised
one. `isSyntheticCloser` names the two constructor-written closers (`forked`, `interrupted`) as a
class. Covered by `TRN-08c`, the synthetic-closer test, and the "no switch exists" test.

as though every call had accounted for itself. What changed is only that this is now stated with
evidence from the target release rather than carried over from `0.1.5`.

## 23. Remaining risks

1. **The target is a release candidate.** `0.1.7-rc.2` may change before `0.1.7` final, and this
   migration would have to be re-verified. The compatibility probes exist to make that cheap: a
   contract change fails `npm run typecheck` rather than a user's profile.
2. **`settings.write` validation depends on `dsh-config-editor` resolving before persisting.** That
   ordering was confirmed by reading the installed source and by the byte-identical patch file in §17,
   but the *rule* that a Host write is schema-validated is upstream's, not this plugin's. The runtime
   keeps its own validation as defence in depth.
3. **A hand-edited profile patch bypasses the editor.** Cross-field errors then surface as
   `plugin.config-invalid` at mount with the runtime refused, which is the same behaviour `0.3.1`
   had; it is documented, not changed.
4. **`plugins.bundle.config` is keyed by package name.** A future rename of the npm package would
   require a matching change to `MAIL_NOTIFY_PACKAGE_NAME`, which is asserted against
   `package.json` — so it fails a test rather than silently unregistering the card.
5. **`Volatile.get()` returns a deeply frozen snapshot** and the schema is flat by necessity. Adding a
   volatile field inside a nested object or a transform is not possible; a future need for one would
   require a schema reshape, and the shape probe records the constraint.

## 25. RC audit correction

This section was added after the audit that reviewed the report above. **The report said `PASS — v0.4.0
RC READY`. That verdict was wrong, and it is left standing here as what was claimed at the time** —
§§1–24 are otherwise unchanged except where a correction is marked in place. What follows is what the
audit found, why each finding was possible, and what now holds instead.

### 25.1 Why the first cross-field-validation conclusion was wrong

The first report concluded that cross-field rules were enforced by the Host before persistence,
because `dsh-config-editor.edit` calls `resolveConfig(fiber.runtime, resolved)` before it writes. The
call is real; the conclusion drawn from it was not.

The error was one of identity, not of reading. Two different functions in this project's dependency
graph are named `resolveConfig`:

| Function | Where it lives | What it does |
| --- | --- | --- |
| `resolveConfig(runtime, config)` | `@deepseek-ai/cordis` (`src/fiber.ts:50`), imported by `dsh-config-editor` | reads `runtime.Config['~standard'].validate(config)` and throws a `ValidationError` when the result carries issues |
| `resolveConfig(raw)` | this plugin, `src/config.ts` | applies the field and cross-field rules and returns a `ConfigResolution` |

The first is the Host's boundary. The second is the plugin's own runtime resolution, reached only from
`src/index.ts`. cordis's `resolveConfig` never calls the plugin's — the only thing they share is the
`Config` schema, and at the time that schema carried field-level constraints alone. So the Host
enforced the port range and the credential grammar, and nothing else; `enabled: true` with an empty
`smtpHost` was field-valid, passed the boundary, and was written to `cordis.patch.yml`.

The audit is the reason this was caught at all: the report's own §7.4 named the mechanism, and the
name collision made the claim read as verified when the code path had never been exercised.

### 25.2 Why the first invalid-write test did not cover semantic invalidity

§17 exercised two writes: `smtpPort = 99999` and `smtpPasswordCredential = "not a valid ref!"`. Both
are **field-level** violations. They are refused by the field schemas, and they would have been
refused by an implementation with no cross-field rules whatsoever — which is exactly what the
implementation was. The test was therefore unable to distinguish a working configuration boundary from
a missing one, and it reported PASS for the missing one.

The generalisable defect is the choice of cases, not the harness: the two candidates were selected
because they were easy to construct through the API, and neither of them was *semantically* invalid.
A boundary test has to include at least one candidate that every field-level rule accepts and the
product rejects.

### 25.3 How `.check()` was verified

The task's brief described a Schemastery `.check()` for cross-field Config validation, and the DSH
`0.1.7` cookbook states it runs on the Host before persistence and is omitted from serialized form
schemas. The pinned release has no such method.

`scripts/probe/config-check-probe.mjs` was written to establish this from the installed code rather
than from documentation. It enumerates `Schema.prototype` and finds the complete set — `~standard`,
`toJSON`, `set`, `push`, `i18n`, `extra`, `required`, `disabled`, `collapse`, `hidden`, `loose`,
`deprecated`, `experimental`, `pattern`, `simplify`, `toString`, `role`, `default`, `link`, `comment`,
`description`, `max`, `min`, `step`, `volatile` — with no `check`, and it reports
`typeof Schema.prototype.check === 'undefined'`. It runs twice per invocation of the acceptance gate:
once against this checkout's copy and once with `SCHEMA_PROBE_MODULES` pointed at the copy inside the
installed DSH `0.1.7-rc.2`. Both copies are `3.18.4` and both agree.

The mechanism that does exist at that exact boundary is the standard-schema contract, and the probe
establishes all five properties the task named for it: the validator's input is the primitive
candidate and its `value` is the volatile tree; a root object with `.volatile()` children remains a
valid form whose fields the settings walk still sees; a failing product check produces issues that
cordis turns into a thrown `ValidationError`, so the refusal precedes any write; and the check is
absent from the serialized form, because `toJSON()` carries no functions and the form projection is
rebuilt from it. `docs/DECISIONS.md` D021 §2.1 holds the result table.

### 25.4 How prompt attribution moved to source semantics

`docs/CONFIG_SPEC.md` said the field carries *"该 Turn 最近一条用户消息"* — the turn's most recent user
message. The first implementation delivered something else: the turn's **first** non-whitespace
user-role message, by position, with every later one discarded as injected context.

The rule was adopted because the recorded v4 lifecycle writes the operator's prompt and then two
injected context messages, and a latest-wins rule had rendered the reminder instead. That observation
was correct. The repair was not: it replaced one positional rule with another, and position is exactly
what the runtime does not promise. DSH's `UserMessage` carries a required `source`, the base contract
defines a direct human message as `{ kind: 'user' }`, and every other producer declares its own kind —
`runtime-context`, `agent-instructions`, `skill-catalog`, `goal`, `webhook`, `agent-message`,
`subagent-settled`, and more. The kinds are the guarantee; the order is an observation.

Attribution is now: the turn's most recent `user/message` whose `source.kind === 'user'`. A message
with any other, absent, or malformed kind never claims and never replaces the prompt, whatever its text
and whenever it arrives. The adapter copies `sourceKind` as one scalar and retains nothing else — not
the source object, and not any payload inside it.

The `CONFIG_SPEC` sentence was **not** changed to "first message". The product semantic remains "the
most recent one"; what changed is that "user message" is now defined by its source rather than by its
position in the log. The reordering tests written for this closure permute the injected messages
deliberately, because the recorded corpus happens to write the prompt first and a positional rule
would pass against it.

### 25.5 Was the `parentSession` subagent false positive corrected?

Yes. `dsh-session` documents `parentSession` as *"the session this one was forked from (seed
lineage)"* — lineage, not agency — while the two positive criteria are `origin: 'subagent'` and a
strictly positive `delegationDepth`. `SessionStore.fork()` writes `parentSession` and `isSeeded: true`
and neither of the other two, so a fork the operator created was classified as a subagent and its
turn, question, and approval notifications were all suppressed under the default
`includeSubagents: false`.

This risk was identified and documented in Phase 8.1 (`docs/DECISIONS.md` A15), which concluded that
no real subagent was being misclassified and therefore left the three-criterion rule alone. That
reasoning conflated two questions: whether real subagents are misclassified, and whether the criterion
proves what it is used for. Every real subagent also carries `origin`, so removing `parentSession`
cannot lose one — while keeping it silently drops the operator's own forks. The criterion is removed;
`parentSession` is carried on `SessionFacts` as metadata that no branch consults.

## 27. Web configuration completeness closure

§25 closed four audit findings and re-ran every gate under §26. It did not close this one, because no
gate in the suite could see it. This section records the defect, why the previous evidence was unable
to detect it, the invariant that now detects its whole class, and the browser run that replaces §18's
count with identification.

### 27.1 The defect, and why "23 controls" could not see it

`ALL_FIELDS` in `src/client/fields.ts` carried **22** `FieldDef`s. The Host `Config` declares **23**
fields. The omitted one was:

```text
minTurnDurationMs
```

It is the settled-turn suppression threshold: `Schema.natural().min(0).max(3_600_000).default(0)`,
consumed by `src/notifier.ts` at the `below-min-duration` branch. With no `FieldDef`, the card rendered
no control for it, so the field was configurable only by hand-editing the profile patch — the exact
outcome the Web surface exists to remove — and `MailNotifyCard.resetAll()`, which iterates
`ALL_FIELDS`, silently did not stage its removal either. Two defects, one cause.

The previous browser smoke counted **23 labelled controls** and read that as confirmation:

```text
22 Config controls  +  1 write-only password control  =  23 labelled controls
```

The count was correct; the inference was not. The password is a **Credential value** written through
the `credentials` domain, not a Config field, so a total that includes it cannot bound the Config
field set from either side: 22 + 1 and 23 + 0 are the same number, and the second is the only one that
was ever true. A control count is invariant under a swap between the two categories, which is why it
could not falsify `23 Config controls` and why the report's §18 row and its "all 23 fields appeared"
sentence are, as evidence for Config completeness, void.

The defect class is larger than the field. Nothing in the suite compared the Web form against the Host
schema. `FLD-01` asserted a **handwritten list of 22 names**, so it encoded the defect rather than
catching it: a field added to the schema and never exposed left both the schema test and the card test
green, because each was checked against its own copy of the same omission.

### 27.2 What changed

| Change | File |
| --- | --- |
| `FieldDef` for `minTurnDurationMs`: `kind: 'natural'`, `min: 0`, `max: 3_600_000`, placed after `notifyMaxTokens` in the notifications group and outside the human-attention block | `src/client/fields.ts` |
| `labelMinTurnDuration` / `hintMinTurnDuration` in both dictionaries | `src/client/locale.ts` |

No Host Config field, bound, default, or policy semantic was touched. The change is an exposure fix:
`src/config.ts`, `src/notifier.ts`, `src/human-attention.ts`, and `src/index.ts` are unchanged, and the
policy suite passes unmodified (§28).

The hint states the four facts the field's semantics require, in both languages:

```text
EN  Suppresses settled Turn notifications whose known duration is below this many milliseconds.
    0 disables duration filtering, and an unknown duration is never suppressed.
    Question and approval notifications ignore it.
ZH  已知耗时低于该毫秒数的已结算任务通知会被抑制。0 表示不按耗时过滤；耗时未知时不抑制。
    提问与批准通知不受该项影响。
```

The labels are `Minimum turn duration` and `最短任务时长`. Both are unitless, matching the existing
vocabulary (`Retry base delay`); the unit is carried by the hint, and the bounds are carried by the
`schema (0 … 3 600 000)`, so the control is usable without reading this report.

### 27.3 The invariant that replaces the count

`tests/support/host-fields.ts` derives the Host field set from the schema's **own serialization**:

```text
Config.toJSON()  →  { uid, refs }        a table of nodes keyed by numeric uid
root node        →  .dict                field name → uid of that field's node
```

That pair is exactly how `dsh-settings`'s form projection recovers field names from the same
serialization, so the comparison is a statement about the form DSH renders rather than about the
schema object in memory. `Config.dict` would answer the same question in one step, but `toJSON()` is
the documented serialization and is already the projection `CFG-11`/`CFG-13` check, so the invariant
is stated in the terms the Host's own walk uses. It throws rather than returning an empty list when the
serialized shape is not what it expects, because an empty Host side would make every comparison
vacuous.

`FLD-01` and `PAR-01`…`PAR-06` (`tests/client/config-surface.test.ts`) then assert a **key-set
equality in both directions**:

| Assertion | Row |
| --- | --- |
| `set(ALL_FIELDS.field) == set(Host Config fields)` | `FLD-01`, `PAR-01` |
| A Host field the Web UI omits fails | `PAR-01` (`missingFromWeb`) |
| A Web field the Host does not declare fails | `PAR-01` (`unknownToHost`) |
| A name declared twice on either side fails | `PAR-01`, `PAR-02` |
| Every Host field is volatile, so a save reaches the running plugin | `PAR-03` |
| The 23-field size and `minTurnDurationMs` are named as independent statements | `PAR-02` |
| The password is a credential, not a 24th Config field | `PAR-04`, `PAR-05` |
| The expanded card renders 23 Config controls **and** one password control | `PAR-05` |

The size assertion is deliberately **not** the invariant. It is a second statement about this release
that no key-set equality can satisfy on its own, and `PAR-02` keeps it beside the named field so a
future controller of this report sees both the generic rule and the specific membership the previous
closure needed. `tests/unit/settings.test.ts`'s `EDITABLE_FIELDS` was switched to the same derivation,
so `CFG-11` and `CFG-13` no longer check a copy of their own expected input.

`Reset All` coverage follows from the fix and is asserted directly (`RST-01`…`RST-05`): with a
user-layer `minTurnDurationMs: 60000` present, `Reset All` stages `unset ["minTurnDurationMs"]` among
its 23 unsets, `Save` removes the user-layer key, and the effective value re-inherits the composition
layer. The per-field `Reset`, an edited value's numeric staging, and the out-of-range refusal are
covered beside it.
